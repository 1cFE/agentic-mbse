## Problem Statement

### Current State

fusion-tea uses the legacy `modeling_pm/` flat directory structure:
- All project management in `modeling_pm/` with subdirectories `active/`, `backlog/`, `research/`, `learnings/`, `docs/`
- `SOURCE_INDEX.md` at project root
- No structured registry files (KNOWLEDGE.md, ARCHITECTURE.md, REQUIREMENTS.md, VALIDATION_MATRIX.md)
- No YAML frontmatter on work item artifacts
- No `data/` directory

### Desired Outcome

fusion-tea uses the 4-directory architecture (`knowledge/`, `modeling_project/`, `work/`, `data/`) with all registry files populated, YAML frontmatter on work item artifacts, and the BACKLOG.md restructured as a machine-readable dashboard.

## Scope

### In Scope

1. File moves from `modeling_pm/` to new locations
2. Creating and populating new registry files from existing content
3. Adding YAML frontmatter to existing work item artifacts
4. Restructuring BACKLOG.md with YAML frontmatter
5. Creating new empty directories for the full structure
6. Running `agentic-mbse init --dev` to produce fresh tool-owned files at new locations (preserving symlinks)
7. Updating fusion-tea CLAUDE.md
8. Updating `.gitignore`
9. Removing `modeling_pm/` after manual audit and approval
10. Branch management (checkout `agentic-mbse-refactor`, merge back on completion)

### Out of Scope

- Changes to `models/`, `tests/`, or `.claude/` symlinks
- Work item directory renaming to `{WI-XXX}_{name}/` format (deferred to PM engine)
- Archiving completed work items to `work/completed/` (deferred — requires WI-XXX IDs for the `YYYYMMDD_{WI-XXX}_{name}/` convention; completed items stay in `work/active/` with `Status: completed` until the PM engine handles archival)
- Restructuring OVERVIEW.md with Goals Registry (G-XXX) and Analysis Questions (AQ-XXX) tables (the template was updated in D1.2 but populating the structured format for fusion-tea is a content task best done during an `/onboard` session, not a mechanical migration)
- Command refactoring (Epic 3)
- PM engine code (Epic 4)
- Changes to the agentic-mbse codebase itself

### Edge Cases & Considerations

- **MODELING_GUIDE.md and MODELING_PROCESS.md**: These are tool-owned and will be regenerated by `agentic-mbse init`. The old copies in `modeling_pm/` (if they exist as real files rather than symlinks) should be kept until manual verification confirms the new copies are correct, then deleted.
- **LOCAL_GUIDE.md**: Content must be extracted into PR-XXX entries in REQUIREMENTS.md before deletion. Deletion happens only after manual audit and approval.
- **Epic backlog files**: `modeling_pm/backlog/epic-cost-patterns-derisking.md` and `sysml-codegen-upgrade.md` move to `work/backlog/`. The non-epic-prefixed file (`sysml-codegen-upgrade.md`) should be renamed to follow the `epic-{name}.md` convention.
- **Research docs with non-standard names**: Two files (`NEXT_cost-architecture-patterns.md`, `heirarchical-cost-modeling-mbse-patterns.md`) don't follow the `YYYYMMDD-HHMMSS_topic.md` naming convention. Move as-is to `knowledge/research/approved/`.

### Key Decision: Legacy Work Item Directory Names

Existing work item directories keep their current names (e.g., `cost-patterns-demo/`) without WI-XXX prefixes. Directory renaming to `{WI-XXX}_{name}/` is deferred to the PM engine (Epic 4). However, WI-XXX IDs ARE assigned in BACKLOG.md frontmatter during this migration to make the YAML schema-compliant per frontmatter-schemas.md § 3.5 and DD-2 (BACKLOG.md is the ID registry).

### Key Decision: Completed Items Stay in `work/active/`

`foundation-package` and `power-balance-calculations` have `Status: completed` but remain in `work/active/` rather than moving to `work/completed/`. The architecture requires `work/completed/YYYYMMDD_{WI-XXX}_{name}/` format, which depends on WI-XXX IDs being reflected in directory names. Archival is deferred to the PM engine.

### Key Decision: BACKLOG.md Epics vs Standalone

Only items with existing decomposition files are listed as `epics` in the BACKLOG.md YAML:
- Cost Modeling Patterns De-Risking (has `epic-cost-patterns-derisking.md`)
- sysml-codegen Upgrade (has `epic-sysml-codegen-upgrade.md`)

All other items (including completed "epics" like Foundation Package and Power Balance, and future roadmap items like Power Core Definitions, Magnet System, etc.) are listed as `standalone` items. They will be promoted to epics with decomposition files when they enter the pipeline. This avoids implying decomposition structure that doesn't exist.

### Key Decision: P0.5 Maps to P0

The "Costed Component Interface" item at P0.5 maps to `P0` in the YAML schema, which only supports P0/P1/P2/P3. Rationale: it blocks P1 work, making it effectively P0.

### Key Decision: Deferred Deletion with Audit Gates

Two audit gates before destructive operations:
1. **Gate 1**: After tool-owned files regenerated and LOCAL_GUIDE.md extracted → user audits and approves deletion of `modeling_pm/LOCAL_GUIDE.md`, `modeling_pm/MODELING_GUIDE.md`, `modeling_pm/MODELING_PROCESS.md`
2. **Gate 2**: After all moves complete and tests pass → user audits and approves deletion of `modeling_pm/`
