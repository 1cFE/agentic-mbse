What we're building, and how we test it

A shared rulebook describes a defined set of execution capabilities. L6, codegen and guidance use those decisions. Independent tests compare the rulebook with the generator on retained boundary models.

Status: draft epic and feasibility prototypes. The production profile, integrated check command and new snapshot-policy integration are not implemented or proven by this explainer.

The problem today

  • The generator, L6 and guidance have useful existing shared contracts, but incomplete agreement about supported execution shapes.
  • dc3's native models used constructs the generator could not handle. They did not pass L6 cleanly: L6 reported String and constraint findings but missed other capability boundaries. The owner explicitly allowed a native result with generated readiness parked.
  • Earlier work tested prefix semantics, attachment, and particular binding guidance separately. It did not systematically test complete published examples across those dimensions. Known hazards also remained in fixture notes and backlog entries.

The proposed design

  • Rulebook: shared facts and pure capability decisions, with exact context, admitted/refused/excluded/omitted outcomes, evidence and remedies. The proposal keeps it in agentic-mbse so L6 needs no reverse dependency; policy ownership still needs a documented boundary decision.
  • L6: reports the supported structural assessment and any checks it could not complete. It does not promise to predict every generation or runtime failure.
  • Generator and check: use shared decisions once their required facts are available, including occurrence evidence where needed. Both use the same read-only preparation path through elaboration, projection and generation preflight. check stops before output mutation; passing it does not certify runtime or handwritten implementation correctness.
  • Guidance: the capability page is rendered from reviewed records. Separate example tests verify published recommendations and expected limitations.
  • Independent “referee” tests: run refused cases and accepted near-neighbors through the rulebook and the underlying generator route without the new screen. Covered disagreements fail CI. This cannot prove agreement for every possible model.

Two additional controls broaden coverage:

  • Refusal inventory: enumerate recognized diagnostic constructors, factories and raises, then classify their meaning and ownership. New recognized sites fail the inventory guard until reviewed. A static scanner has syntax and reachability limits; annotations do not establish behavioral coverage.
  • Example manifest: account for executable examples, definitions, expected negatives, native-only cases and justified fragments. Hash-pinning a fragment detects edits; it does not prove the example executes.

One example, traced through

A modeler puts an assert constraint inside a calc.
  1. The shared rule records the pinned generator's attachment refusal and its tested boundary.
  2. L6 reports that assessed capability with its location and remedy, alongside independently evaluable findings.
  3. The rendered docs explain part-owned assertions as an alternative, including the semantic difference: a generated verdict alone does not preserve a native fail-closed guard.
  4. The fixture independently verifies the refusal and the admitted alternative. Other unresolved execution requirements remain visible.
A developer adds a recognized refusal site.
  1. The inventory guard fails until the site is reviewed and classified.
  2. A shared capability refusal gets a rule, diagnostic mapping and boundary fixtures. A codegen-specific, malformed-input, environmental or snapshot check gets its own appropriate coverage instead.
  3. The independent tests verify behavior on covered cases; rendering and example checks enforce the affected guidance contract.

Boundary findings incorporated into the epic

  • List inputs: an ordered nonunique calc input bound to a scalar generates in the retained fixture. A literal sequence actual (a, b) is refused. Do not ban the declaration or assume every other list form is supported.
  • Arithmetic actuals: in v = rate * fuel_code is refused in its fixture. It is now explicit candidate ES-012, beyond dc3's categories.
  • Computed reason strings: five call sites exceed the prototype scanner's resolver, but production already has a fixed 27-member REASON_CODES set and rejects unknown reasons. Map and test those emissions; a new enum is not required by this finding.
  • Uncoded sites: 137 free-text and 130 builtin candidate sites need classification. Public capability failures need stable reasons; not every exception needs a new code or an unreachable-model justification. The old ten-day estimate has been withdrawn.
  • Silent losses: each known family needs retained semantic presence/absence evidence, including allowed metadata omission. Name-substring checks in the prototype are preliminary.
  • Part counts: production must use effective reachable occurrences and resolved bounds. A typing or exact redefinition elsewhere cannot settle another instance's bounds.

Input order: a demonstrated cross-route mismatch

For the retained subtraction model with intended a = 10 and b = 3, reversed unprefixed declarations in b = 3; in a = 10; evaluate to −7 natively and 7 through the pinned generator and TEAx. Reversed explicit in :>> b = 3; in :>> a = 10; evaluates to 7 on both tested routes. Deliberate explicit renaming is also valid.

Item 4 records resolved implicit mismatches without treating every rename as an error. It must retain the cross-route counterexample and record an upstream disposition. Generation success is insufficient evidence of agreement with native semantics.

fusion-tea: the prototype and independent rerun report 125 mismatches at the pinned revision. The complete affected fusion-tea routes were not regenerated or evaluated in this investigation, so their harmlessness is not established. The approved policy blocks new mismatches and keeps explicitly pinned legacy cases as visible warnings until a separately authorized migration.

What remains unproven

  • Coverage outside the retained fixtures; the independent oracle is finite and several rules need richer occurrence/context evidence.
  • The new shared read-only check path, snapshot authority integration, replay parity and package-skew behavior.
  • Semantic omission assertions beyond the prototype's text-name checks.
  • Executable guidance coverage beyond the current manifest; some fragments are useful teaching material and need not become runnable unless that broader scope is selected.

Agreed scope and requirements

The owner approved D1, D2 and D3. These are requirements for the planned work, not implemented behavior; other design decisions remain in the epic, which is the authoritative decision record.

  • D1 — Approved: block new positional mismatches; warn on explicitly pinned legacy cases until migration. Migration is separate work, and accepting legacy warnings does not certify native/generated equivalence.
  • D2 — Approved: inspect and classify all 500 recorded candidate sites (441 codegen, 59 agentic-mbse), reconciling changes at implementation time. Account for each as in scope, already handled elsewhere, or explicit follow-up. Implement only the scoped shared checks; this does not commit to building 500 rules.
  • D3 — Approved: retained executable or exact expected-negative evidence for 100% of generated-use recommendations and remedies. Justified pure teaching fragments can remain exempt.

Other design decisions remain in the epic: shared policy ownership, exclusion/metadata severity, remaining capability gaps and coordinated guidance changes. The plan does not add language support or authorize edits to consumer models by itself.
