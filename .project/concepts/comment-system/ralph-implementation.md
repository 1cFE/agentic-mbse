# Setting Up Ralph for the Markdown Comment Threads Project

## Overview

This guide walks through setting up a "real" Ralph loop (bash-based, fresh context per iteration) to build the markdown commenting system designed in the `Markdown comment threads` conversation. The goal is to spin this up in a git worktree and let Ralph crank overnight.

**Key principle:** Ralph's effectiveness is 90% in the setup — the specs, the prompts, and the backpressure. The loop itself is trivial.

---

## Prerequisites

- Claude Code CLI installed and configured
- Git repository for the project
- `--dangerously-skip-permissions` comfort level (run in a sandboxed environment or Docker if preferred)
- UV + Python (your preferred environment)

## Step 1: Create the Worktree

```bash
# From your main repo
git worktree add ../comment-system-ralph -b ralph/comment-system

cd ../comment-system-ralph
```

## Step 2: File Structure

Create this structure before running anything:

```
comment-system-ralph/
├── loop.sh                    # The outer bash loop (provided below)
├── PROMPT_plan.md             # Planning mode prompt (generate with meta-prompt)
├── PROMPT_build.md            # Building mode prompt (generate with meta-prompt)
├── AGENTS.md                  # Operational guide — build/test/lint commands
├── IMPLEMENTATION_PLAN.md     # (Generated by Ralph in planning mode)
├── specs/                     # One markdown file per topic of concern
│   ├── data-model.md          # Sidecar JSON schema, thread/comment/anchor model
│   ├── anchor-reconciliation.md  # Content hash → fuzzy match → line offset
│   ├── cli-interface.md       # comment add/list/reply/resolve/reconcile commands
│   ├── mcp-server.md          # MCP tools for agent interaction
│   └── vscode-extension.md    # (Phase 2 — can defer or include for planning)
└── src/                       # Application source (starts empty or with scaffold)
```

## Step 3: `loop.sh` — The Enhanced Loop

This is the Clayton Farr playbook version with mode selection and max-iterations.

```bash
#!/bin/bash
# Usage: ./loop.sh [plan] [max_iterations]
# Examples:
#   ./loop.sh              # Build mode, unlimited iterations
#   ./loop.sh 20           # Build mode, max 20 iterations
#   ./loop.sh plan         # Plan mode, unlimited iterations
#   ./loop.sh plan 5       # Plan mode, max 5 iterations

# Parse arguments
if [ "$1" = "plan" ]; then
    MODE="plan"
    PROMPT_FILE="PROMPT_plan.md"
    MAX_ITERATIONS=${2:-0}
elif [[ "$1" =~ ^[0-9]+$ ]]; then
    MODE="build"
    PROMPT_FILE="PROMPT_build.md"
    MAX_ITERATIONS=$1
else
    MODE="build"
    PROMPT_FILE="PROMPT_build.md"
    MAX_ITERATIONS=0
fi

ITERATION=0
CURRENT_BRANCH=$(git branch --show-current)

echo "━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━"
echo "Mode:   $MODE"
echo "Prompt: $PROMPT_FILE"
echo "Branch: $CURRENT_BRANCH"
[ $MAX_ITERATIONS -gt 0 ] && echo "Max:    $MAX_ITERATIONS iterations"
echo "━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━"

# Verify prompt file exists
if [ ! -f "$PROMPT_FILE" ]; then
    echo "Error: $PROMPT_FILE not found"
    exit 1
fi

while true; do
    if [ $MAX_ITERATIONS -gt 0 ] && [ $ITERATION -ge $MAX_ITERATIONS ]; then
        echo "Reached max iterations: $MAX_ITERATIONS"
        break
    fi

    cat "$PROMPT_FILE" | claude -p \
        --dangerously-skip-permissions \
        --output-format=stream-json \
        --model sonnet \
        --verbose

    # Push changes after each iteration
    git push origin "$CURRENT_BRANCH" 2>/dev/null || {
        echo "Failed to push. Creating remote branch..."
        git push -u origin "$CURRENT_BRANCH"
    }

    ITERATION=$((ITERATION + 1))
    echo -e "\n\n======================== LOOP $ITERATION ========================\n"
done
```

> **Model choice:** The playbook uses `--model opus` for complex reasoning. For a
> well-specced project like this, `sonnet` is a reasonable default to keep costs down.
> Switch to `opus` if Ralph struggles with architectural decisions. You could also
> use `opus` for planning and `sonnet` for building.

Make it executable:

```bash
chmod +x loop.sh
```

## Step 4: Generate the Supporting Files

This is where most people go wrong. The specs, prompts, and AGENTS.md are the
context engineering that makes Ralph succeed or fail. Don't hand-write them from
scratch — use a conversation with Claude to generate them from your design doc.

### The Meta-Prompt: Generating Ralph Files from a Design Doc

Use this prompt in a **separate Claude conversation** (not in the Ralph loop).
Paste your design document (the full sidecar JSON spec, anchor model, CLI interface,
etc. from the `Markdown comment threads` conversation) as context.

---

#### Meta-Prompt for `specs/*`

```
I'm setting up a Ralph Wiggum loop to build the system described in the
attached design document. Ralph loops work by having an AI agent iterate
in a bash loop, each iteration getting fresh context. The agent reads
specs, picks a task from an implementation plan, implements it, runs
tests, commits, and exits. The bash loop restarts with a clean context.

I need you to break this design into individual specification files for
a `specs/` directory. Each spec should cover ONE topic of concern — a
distinct capability area that can be described in one sentence without
using "and" to conjoin unrelated things.

For each spec file, include:
1. **Purpose** — One sentence describing what this component does
2. **Requirements** — Behavioral outcomes, not implementation details.
   What observable results indicate success?
3. **Acceptance criteria** — Specific, testable conditions. Write these
   as "Given X, when Y, then Z" or similar verifiable statements.
4. **Interfaces** — How this component connects to others (inputs,
   outputs, data formats). Reference other spec files by name.
5. **Constraints** — Non-negotiable rules (e.g., "source files are
   NEVER modified", "all operations are deterministic")
6. **Out of scope** — Explicitly state what this spec does NOT cover
   to prevent Ralph from wandering.

Guidelines:
- Keep each spec under 200 lines. Token efficiency matters.
- Use plain markdown, not JSON. Better token efficiency for LLMs.
- Acceptance criteria should be machine-verifiable where possible.
  "Tests pass" > "Looks correct."
- Think about what backpressure looks like for each spec.
  What tests would reject bad work?
- Order the specs roughly by dependency (foundational → dependent).

Produce the specs as separate markdown code blocks, each with a
filename header like `## specs/data-model.md`.

<design_document>
[PASTE YOUR FULL DESIGN DOC HERE]
</design_document>
```

---

#### Meta-Prompt for `AGENTS.md`

```
I'm setting up a Ralph Wiggum loop for a Python project (using UV for
package management, pytest for testing, ruff for linting, mypy for type
checking). The project is a markdown commenting system with a CLI, an
MCP server, and eventually a VSCode extension.

Generate an AGENTS.md file. This is the operational guide that gets
loaded into EVERY Ralph loop iteration. It must be:

- BRIEF (~60 lines max). Every token here costs context in every iteration.
- OPERATIONAL ONLY. No status updates, no progress notes, no changelogs.
  Those go in IMPLEMENTATION_PLAN.md.
- Focused on HOW TO BUILD AND TEST, not what to build.

Include:
1. **Build & Run** — How to install deps, run the project, start dev mode
2. **Validation** — Exact commands for tests, typecheck, lint
3. **Codebase Patterns** — Key conventions Ralph should follow:
   - Project structure expectations
   - Import conventions
   - Error handling patterns
   - Any critical rules (e.g., "never modify source markdown files")
4. **Known Gotchas** — Things that commonly trip up agents:
   - Environment setup quirks
   - Test runner configuration
   - File path conventions

Keep it to facts and commands. No prose. No explanations of why.
Ralph doesn't need persuading — he needs instructions.
```

---

#### Meta-Prompt for `PROMPT_plan.md`

```
Generate a PROMPT_plan.md for a Ralph Wiggum loop. This prompt is piped
into `claude -p` at the start of each planning iteration. The agent
should:

1. Study all specs in specs/* using parallel subagents
2. Study IMPLEMENTATION_PLAN.md if it exists
3. Study src/ to understand what's already built
4. Compare specs against current code (gap analysis)
5. Create/update IMPLEMENTATION_PLAN.md with prioritized tasks

Rules:
- This is PLANNING ONLY. No implementation. No commits.
- Tasks should be sized for ONE iteration (one fresh context window).
  If a task would require reading/modifying more than ~5 files, break
  it down further.
- Each task should reference which spec(s) it addresses.
- Each task should note what backpressure verifies it (which tests,
  which typecheck, which lint rules).
- Use "study" not "read". Use "don't assume not implemented" as a
  guardrail. Use "Ultrathink" for complex analysis.
- Prefer markdown bullet points over JSON for the plan.
- The project uses Python with UV, pytest, ruff, mypy.

The prompt should fit in ~30 lines. Every token matters.
```

---

#### Meta-Prompt for `PROMPT_build.md`

```
Generate a PROMPT_build.md for a Ralph Wiggum loop. This prompt is piped
into `claude -p` at the start of each build iteration. The agent should:

1. Study specs/* for requirements context
2. Study IMPLEMENTATION_PLAN.md to pick the most important remaining task
3. Search the codebase before assuming anything is missing
4. Implement exactly ONE task
5. Run validation (pytest, mypy, ruff)
6. Update IMPLEMENTATION_PLAN.md — mark task done, note discoveries
7. Update AGENTS.md ONLY if operational learnings (new commands, gotchas)
8. git add -A && git commit with descriptive message

Include these guardrails (using the 9s numbering convention):
- 999: Capture the why in docs and tests
- 9999: Single sources of truth, no migrations/adapters
- 99999: Implement completely. No placeholders, no stubs.
- 999999: Keep IMPLEMENTATION_PLAN.md current with learnings.
- 9999999: Update AGENTS.md with operational learnings only, keep it brief.
- 99999999: For bugs found, resolve or document in IMPLEMENTATION_PLAN.md.
- 999999999: Clean completed items from IMPLEMENTATION_PLAN.md periodically.
- 9999999999: AGENTS.md is operational only — no status, no progress notes.

The prompt should fit in ~40 lines. Concise > verbose.
The project uses Python with UV, pytest, ruff, mypy.
```

## Step 5: Execution Sequence

### Phase 1 — Generate Files (human + Claude conversation)

1. Open a fresh Claude conversation
2. Paste your design document from the `Markdown comment threads` chat
3. Run the **specs meta-prompt** → save each output to `specs/*.md`
4. Run the **AGENTS.md meta-prompt** → save to `AGENTS.md`
5. Run the **PROMPT_plan.md meta-prompt** → save to `PROMPT_plan.md`
6. Run the **PROMPT_build.md meta-prompt** → save to `PROMPT_build.md`
7. Review all files. This is your last high-leverage intervention before
   Ralph runs. Spend time here.

### Phase 2 — Planning (Ralph generates the implementation plan)

```bash
./loop.sh plan 3
```

This runs 1-3 planning iterations. Ralph will:
- Read all specs
- Analyze the (empty) src/ directory
- Generate `IMPLEMENTATION_PLAN.md` with prioritized tasks

**Review the plan before building.** This is your second-to-last
checkpoint. If the plan is wrong, re-run planning or adjust specs.

### Phase 3 — Building (Ralph implements)

```bash
# Start with a capped run to watch the first few iterations
./loop.sh 5

# If it's working well, let it run longer
./loop.sh 30

# Or go full YOLO (Ctrl+C to stop)
./loop.sh
```

### Phase 4 — Observe and Tune

Especially for the first 3-5 iterations, **watch what Ralph does.**

- Is it picking reasonable tasks from the plan?
- Are tests actually providing backpressure?
- Is it going in circles on something?
- Is AGENTS.md staying lean or getting bloated?

Common tuning actions:
- Add a guardrail to the prompt ("don't do X")
- Add a pattern to src/lib/ that Ralph will discover and follow
- Regenerate the plan if it's gone off track: `./loop.sh plan 2`
- Add a utility or fixture that steers Ralph toward correct patterns

## Cost Expectations

Rough estimates per iteration (will vary significantly):

| Model | Per Iteration | 30 Iterations |
|-------|--------------|---------------|
| Sonnet | ~$0.50-2.00 | ~$15-60 |
| Opus | ~$2.00-8.00 | ~$60-240 |

For a first experiment, cap at 10-15 iterations with Sonnet. You'll get a good
signal on whether the specs and prompts are working before committing to a longer run.

## Recommended Initial Scaffold

Before running Ralph, create a minimal project skeleton so it has
something to discover and extend (rather than making all the structural
decisions itself):

```bash
# Project root
uv init
uv add --dev pytest ruff mypy

# Source structure
mkdir -p src/comment_system
touch src/comment_system/__init__.py
touch src/comment_system/models.py      # Data model lives here
touch src/comment_system/anchors.py     # Anchor reconciliation
touch src/comment_system/storage.py     # Sidecar file I/O
touch src/comment_system/cli.py         # Click/Typer CLI entry point

# Test structure
mkdir -p tests
touch tests/__init__.py
touch tests/conftest.py

# Initial commit
git add -A
git commit -m "initial scaffold for comment system"
```

This gives Ralph "signs" about where things should go without
prescribing implementation details.

## Recovering from Problems

| Problem | Solution |
|---------|----------|
| Ralph is going in circles | `Ctrl+C`, inspect IMPLEMENTATION_PLAN.md. Likely a task that's too big or specs that are ambiguous. Fix specs or break up the task, then resume. |
| Ralph bloated AGENTS.md | Manually trim it back to ~60 lines. Add a stronger guardrail to PROMPT_build.md. |
| Tests aren't catching bad work | Your backpressure is too weak. Add more specific test fixtures or assertions. |
| Plan is stale/wrong | `./loop.sh plan 2` to regenerate. Plans are disposable. |
| Ralph makes wrong architectural decisions | Add the correct pattern to `src/` as a utility. Ralph discovers and follows existing patterns. |
| Ralph assumed something wasn't implemented | Add emphasis to "don't assume not implemented — search first" in the prompt. This is the most common failure mode. |
| Cost is running away | Switch to `--model sonnet`, reduce max iterations, tighten task scope in specs. |
